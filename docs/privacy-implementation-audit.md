# Implementation-based privacy audit

Inspected October 9, 2026. Scope: the current bundled Capacitor iOS app and its Firebase/recovery/import implementation. This is a code audit, not legal advice or certification of deployed cloud configuration. No application code was changed. No private environment values or user records were needed.

Draft policy: [privacy-policy.md](privacy-policy.md). All editorial `[CONFIRM …]` items must be resolved before publication.

## Findings

| Topic | Implemented behavior and evidence |
| --- | --- |
| 1. Local data categories | Complete account dataset: journal/reflections/assessments, timer/activity presets, cycle history/settings, books, widget preferences, normalized health records. Also auth sessions, account-access marker, pending mutations/imports, import consent/time, practice and quote checkpoints, and retained legacy local datasets/backups. Models: `src/services/repository-contracts.ts`, `src/domain/{journal,practice,cycle,health}/types.ts`; storage: `src/adapters/firebase/{sync-store,device-access}.ts`, `src/adapters/local/`, `src/platform/runtime.ts`. |
| 2. Cloud categories | Journal entries (including saved practices), timers, activities, books, cycle events, normalized health records, cycle/dashboard settings and repository revision/mutation metadata. All under `users/{uid}`. `src/adapters/firebase/repository.ts`. Runtime timer/quote checkpoints and local import consent are not separately uploaded. |
| 3. Authentication | Email/password Firebase Auth; app uses UID/email. SDK persists sessions using IndexedDB with browser-local fallback, not a custom password store. Accounts are administratively approved through `privateAccess/{uid}`; no in-app registration. `src/adapters/firebase/client.ts`, `src/services/cloud-session.ts`, `firestore.rules`. |
| 4. Journal/practice/books/settings | User-entered content, dates, durations, mood/tags/assessments, timer sounds/configuration, reading metadata and private preferences can persist locally and in cloud. Historical journal cycle context is derived for its own date; legacy persisted context can also exist. `app/YiApp.tsx`, domain types, `src/domain/cycle/journal-context.ts`. |
| 5. Health/body/cycle | Manual temperature, flow/period starts, mucus/sensation/cervix, ovulation/pregnancy tests, intercourse, symptoms, energy/sex drive/PMS, disturbances, medication/free notes and manual sleep measures. Only explicitly recorded fields become manual normalized source records. `src/services/health-service.ts`, `src/domain/cycle/types.ts`. Source dates, identifiers, quality/status and provenance persist; removed manual fields can leave source tombstones. |
| 6. HealthKit permission types | Release reads basal body temperature, menstrual flow and cervical mucus quality. Debug additionally reads sleep, ovulation tests and sexual activity for inspection. `ios/App/App/EquanimityHealthKitPlugin.swift`. `toShare: []`: no writes. No Release automatic sleep source. |
| 7. Eligible imported records | Only verified Tempdrop-origin HealthKit records for those three metrics. Sample UUID, source app/device identifiers, times/timezone, values/units/status and an explicit source/device/HK metadata allowlist persist; arbitrary raw metadata/JSON do not. The device identifier is the HealthKit source device's optional local identifier, not an added advertising identifier. `src/domain/health/import-policy.ts`, `src/adapters/healthkit.ts`. |
| 8. Optional consent | Apple permission is separate from default-off UID/device cloud-import consent. Explicit import queries 90 days; retries require the current matching account and consent. No continuous background import. Turning consent off does not erase pending or imported records; permission revocation does not delete copies. `src/services/healthkit-import-service.ts`, `src/application/HealthKitTools.tsx`, repository transaction guards. |
| 9. Offline/recovery | Firestore SDK uses memory cache, while the app stores a complete durable baseline plus UID-owned pending mutations in IndexedDB. HealthKit has a separate durable retry checkpoint. Pending imports merge by source UUID, do not treat missing samples as deletion, and retain superseded/deleted source records. `src/services/cloud-sync.ts`, `src/adapters/firebase/device-recovery.ts`, import service. |
| 10. Sign-out | Closes visible account state, revokes local cached-account reopening and disposes old repository access. Does not delete caches/outboxes/HealthKit consent or batches/runtime checkpoints. A failed SDK sign-out produces a warning to retry before sharing. `src/services/cloud-session.ts`, `src/adapters/firebase/device-access.ts`. |
| 11. Uninstall | Normal iOS Delete App removes app-container storage, not cloud records or Apple Health originals. Offload retains documents/data. No secure-wipe/old-backup guarantee. This platform behavior is not implemented by an app deletion handler. [Apple storage guidance](https://support.apple.com/en-ae/108429). |
| 12. Auth deletion vs Firestore | No `deleteUser` flow, deployed cleanup function or deletion extension configuration in this repository. Auth deletion must not be treated as Firestore erasure. External console extensions cannot be audited here. Google's deletion extension is an additional configured component, not something this code enables. [Firebase deletion extension](https://firebase.google.com/docs/extensions/official/delete-user-data). |
| 13. In-app deletion | Journal entry and saved-timer removal exist, but cloud removal retains the full original record with `deleted: true`. Manual health fields can retain deleted source records. No full account deletion, general UID-cache erasure, or dedicated imported-health deletion UI. `app/YiApp.tsx`, `src/adapters/firebase/repository.ts`, `src/services/health-service.ts`. Existing “This cannot be undone” UI text does not establish server erasure. |
| 14. Personal bundled media | Every installation receives `public/cube-media/cube-01.jpg`–`cube-41.jpg`, `picture-01.jpg`–`picture-43.jpg`, and `wedding.mov`: 85 files. Shared personal quotes are in `app/quotes.ts`. These are app-bundle content, not account-isolated user uploads; there is no photo-library/camera import. Complete file inventory: [beta preparation](private-testflight-beta.md#bundled-personal-media-inventory). |
| 15. Debug/Release logging | Custom lifecycle diagnostics use timing/status/counts, not private record contents; native heartbeat/gong diagnostics are Debug-only. But Capacitor Debug logging prints native response payloads and can expose health results to developer consoles (`node_modules/@capacitor/ios/Capacitor/Capacitor/assets/native-bridge.js`, `CapacitorBridge.swift`). Raw inspection/local export tools are hidden in Release. Release can emit a fixed non-sensitive backup-exclusion warning. No app log-upload endpoint found. |
| 16. Third parties | Firebase Auth/Firestore receive account and saved data; HealthKit is the on-device read interface. Capacitor/React run locally. No shipped Analytics/Crashlytics/ads SDK or remote AI/direct Tempdrop integration. External resource/privacy links and Apple TestFlight involve separate providers. Separate hosted Worker/ChatGPT-auth website code exists, but the standalone iOS build excludes it (`mobile-web/vite.config.ts`). Do not extend this app policy to that website without another audit. |
| 17. Service metadata | Firebase receives normal network/service requests. Google documents Auth IP/user-agent processing for security/abuse prevention. The repository does not determine provider operational logging/retention or deployed console options. No custom hardware/advertising-ID telemetry found. [Firebase privacy documentation](https://firebase.google.com/support/privacy). |
| 18. Retention | No implemented expiry schedule for baseline records, caches or pending writes. Successful queues clear pending state; baselines persist. Sign-out and consent withdrawal do not purge. Cloud and manual health tombstones can retain original content indefinitely. Provider backups/PITR, admin deletion and retention require owner confirmation. |
| 19. Health-data backup | Native helper marks only app `Library/WebKit` excluded from backup, before webview creation and again on foreground. No deletion/relocation/encryption. Exact per-UID/key filesystem control is unavailable through this implementation; OS/WebKit paths can vary, old backups remain, failure warns. Actual physical-device backup verification remains outstanding. `ios/App/App/EquanimityBackupSafety.swift`, AppDelegate/SceneDelegate; [Apple backup guidance](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup). |
| 20. Device-only vs cloud | Active practice/quote checkpoints, consent/import retry state, auth session, account marker and legacy local data are device-only in this architecture. Account baseline/pending edits may contain the same records destined for cloud; completed imports are also cached. Raw inspection is session memory unless a developer exports/logs it. Manual observations are normal account records, not controlled by the separate HealthKit cloud opt-in. |

TestFlight adds platform-level collection even without an app analytics SDK: Apple automatically shares beta crash/usage information with the app provider, without an opt-out, and shares submitted feedback. Invitation method affects name/email visibility. The operator's use and retention still need confirmation. [Apple TestFlight privacy information](https://www.apple.com/legal/privacy/data/en/test-flight/).

## Storage locations and security boundary

- WKWebView persistent origin: `capacitor://equanimity.local`, not a remote server.
- Account snapshot/outbox: IndexedDB `equanimity-cloud-<Firebase project>`, `accounts` store keyed UID. Envelope stores owner, baseline, revision and stable pending mutation identifiers.
- Last allowed account/sign-out tombstone: localStorage `equanimity-cloud-access:<encoded project>:<encoded Firebase app ID>`.
- HealthKit consent, batch and import timestamp: localStorage `equanimity:healthkit:<encoded UID>:{consent|pending|last-import}:v1`. These keys are UID-scoped; unlike the main cache, their key does not separately encode the project.
- Runtime practice/quote state: localStorage `equanimity:runtime:<encoded project>:<encoded UID>:...`.
- Legacy data/backups: `yi-local-data-v1`, `yi-original-backup-v1`, retained legacy `yi-*` localStorage keys. They are device-wide/unowned, not silently uploaded to a new UID.
- Firebase manages its own browser auth persistence. No app-owned password file or native Keychain record is introduced by this implementation.

UID isolation and client security rules are not end-to-end encryption and do not constrain authorized Firebase administrators. Offline cache opening uses the previously locally authorized UID, not a new server-authentication result. An unlocked device with an open account remains a privacy boundary. Sign-out prevents normal visible reuse but is not forensic erasure.

Backup exclusion also affects colocated non-health/auth/pending data. Do not promise that unsynced edits survive backup restore. See [the existing backup investigation and physical verification procedure](private-testflight-beta.md#local-health-storage-and-backup-safety).

## Product changes recommended before TestFlight

- Establish and test a real administrative deletion process before collecting beta users' sensitive records; ensure it removes actual contents and cannot be undone by pending device writes. A configured cloud deletion trigger alone would not erase device caches. Consider a user-facing deletion/cache-erasure workflow next, but do not claim it exists today.
- Make record-removal versus full erasure clear in the UI, especially the existing journal Delete dialog. Full erasure is not currently what its cloud tombstones do.
- Verify native backup exclusion on a physical Release device and a controlled fresh backup using synthetic data; resolve any failure before a real-health-data beta. Existing automated tests/compilation do not establish OS backup contents.
- Approve or deliberately remove bundled personal media before distribution. No media was removed in this audit.
- Resolve the draft's factual decisions, publish it at a stable public HTTPS URL, configure `VITE_PRIVACY_POLICY_URL`, rebuild with `npm run ios:prepare`, and verify Account & data → Privacy in Release. Filling placeholders in a repo file is not publication.
- Treat Debug bridge logs, raw exports and downloaded containers as sensitive. Prefer synthetic accounts for development; consider targeted Debug log suppression for health responses without removing troubleshooting tools.

For later App Store readiness, review Apple's current account-deletion and privacy requirements against the actual account-creation flow and intended audiences. This audit does not certify compliance or require implementing unrelated public-release features now.
